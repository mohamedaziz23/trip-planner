# Analyse complète du projet « Trip Planner PWA »

Cette analyse vient de la lecture du code (API, front, service worker, seed, configs). Je n'ai pas lancé l'application. Je n'ai pas pu lire les PDF de `docs/` : l'outil de rendu PDF n'est pas installé et Python est absent. Tout ce qui suit s'appuie donc sur le code et les README.

## 1. Ce que fait le projet

Trip Planner est une application de planification de voyage collaborative, installable et utilisable hors ligne. Plusieurs personnes préparent ensemble un voyage :

- **Itinéraire** jour par jour sur une carte, avec trajets et temps de déplacement.
- **Budget partagé** multi-devises, avec conversion automatique et calcul de « qui doit combien à qui ».
- **Checklist de valise** générée automatiquement selon le type de voyage, les activités, la saison et les voyageurs.
- **Journal de voyage** avec photos, humeur et géolocalisation.
- **Forum communautaire** avec recherche plein texte et notifications push.

Le projet est découpé en 3 parties :

| Dossier | Rôle |
|---|---|
| `trip-planner-api/` | API REST (Node/Express + MongoDB) |
| `trip-planner-web/` | Front PWA (Next.js/React) |
| `docs/` | 8 PDF : spécification métier et 7 fiches membres (équipe de 7, un module chacun) |

## 2. Architecture globale

```
Navigateur (PWA)
 ├─ React / Next.js  ──────────────► lit/écrit d'abord dans IndexedDB (Dexie)
 ├─ Outbox (file d'écritures en attente)
 └─ Service Worker (/sw.js)  : cache, push, background sync
        │  /api/v1/*  et /uploads/*   (proxy "rewrites" de Next.js)
        ▼
API Express 5  ──► MongoDB 7 (replica set, via Docker)
        ├─► Nominatim (géocodage), OSRM (itinéraire), open.er-api (taux de change)
        ├─► Cloudinary (optionnel) ou dossier ./uploads
        ├─► web-push (VAPID) ; nodemailer (SMTP optionnel)
```

Le **proxy Next.js** est un choix d'architecture important. Le navigateur ne parle qu'à une seule origine (`localhost:3000`). Le cookie de refresh reste donc « first-party », et le service worker peut mettre en cache les appels API. La config est dans [next.config.ts](trip-planner-web/next.config.ts).

## 4. L'API, couche transversale

Tout est sous `/api/v1`. Chaque réponse suit l'enveloppe `{ data, message, errors }` ([lib/http.ts](trip-planner-api/src/lib/http.ts)).

- **[app.ts](trip-planner-api/src/app.ts)** assemble les middlewares, monte les 10 routeurs et expose `/health` et `/uploads` statique.
- **[config/env.ts](trip-planner-api/src/config/env.ts)** lit les variables d'environnement. Les secrets JWT sont obligatoires en production.
- **[config/db.ts](trip-planner-api/src/config/db.ts)** gère la connexion Mongo et `withTransaction`, qui retombe en mode sans transaction si le serveur n'est pas un replica set.
- **Middlewares :**
  - `auth` : `requireAuth`, `optionalAuth` (utilisé par le forum), `requireAdmin`. Chaque requête fait un petit lookup pour que la désactivation d'un compte ou un changement de rôle soit immédiat.
  - `tripAccess` : `loadTripForMember` / `loadTripForOwner`. Toute ressource enfant (lieu, dépense, etc.) passe par là, donc un seul contrôle d'accès.
  - `rateLimit` : 20 tentatives par 15 min sur l'authentification, 300 requêtes par minute en général.
  - `error` : transforme les erreurs zod, Mongoose, multer et le code Mongo 11000 (doublon) en réponses propres.
- **Contrat de synchronisation offline** ([lib/sync.ts](trip-planner-api/src/lib/sync.ts)) :
  - Les créations acceptent un `_id` fourni par le client, donc un rejeu est idempotent.
  - Les mises à jour acceptent `clientUpdatedAt`. Si le serveur a une version plus récente, il répond **409** avec le document serveur (« last-write-wins »).
  - Les suppressions sont idempotentes.

## 5. Les 7 modules

### Module 1 : Utilisateurs (`modules/users/`, collection `users`)
- **Auth** ([auth.routes.ts](trip-planner-api/src/modules/users/auth.routes.ts)) :
  - `register`, `login`, `refresh`, `logout`, `forgot-password`, `reset-password`.
  - Le token d'accès dure 15 min et est gardé en mémoire côté front.
  - Le token de refresh dure 7 jours, dans un cookie httpOnly (path `/api/v1/auth`).
  - Le refresh est **tourné à chaque usage**, avec une tolérance de 15 s pour deux onglets simultanés. La réutilisation d'un ancien token est traitée comme un vol : toutes les sessions sont révoquées ([lib/tokens.ts](trip-planner-api/src/lib/tokens.ts)).
  - Le lien de reset est un token aléatoire de 32 octets, stocké haché (SHA-256), valable 1 h. La réponse est identique que le compte existe ou non. Sans SMTP, le lien s'affiche dans la console.
- **Profil** ([user.routes.ts](trip-planner-api/src/modules/users/user.routes.ts)) :
  - Modification du profil, avatar, mot de passe, préférences de notification, abonnement push.
  - La suppression du compte efface les voyages dont l'utilisateur est propriétaire (en cascade), le retire des autres voyages et **anonymise** ses contenus du forum.
- **Admin** ([admin.routes.ts](trip-planner-api/src/modules/users/admin.routes.ts)) : liste des utilisateurs, activation/désactivation, changement de rôle, statistiques globales avec top 5 des destinations.
- **Fonctionnalité avancée :** export PDF et lien de partage public (hébergés dans le module Trips).

### Module 2 : Voyages (`modules/trips/`, collection `trips`)
- **Modèle** : titre, destination, pays ISO, dates, budget, devise de base, couverture, préférences (type, activités, hébergement, transport, voyageurs, besoins spéciaux), membres (`owner` ou `editor`) et `shareToken`.
- **Routes** ([trip.routes.ts](trip-planner-api/src/modules/trips/trip.routes.ts)) :
  - CRUD et pagination.
  - `GET /trips/:id/full` : renvoie le voyage et tous ses enfants en une seule réponse, pour la copie hors ligne.
  - Gestion des participants : inviter par email (le compte doit exister), retirer, ou quitter.
  - Lien de partage : token de 32 octets, révocable, page publique en lecture seule.
- **Cascade** : [trip.service.ts](trip-planner-api/src/modules/trips/trip.service.ts) supprime lieux, dépenses, checklist et journal avec le voyage, dans une transaction.
- **Export PDF** : [export.pdf.ts](trip-planner-api/src/modules/trips/export.pdf.ts) construit un PDF A4 jour par jour avec pdfkit.
- **Fonctionnalité avancée : synchronisation offline-first.** Elle est décrite en section 7.

### Module 3 : Lieux et itinéraire (`modules/places/`, collection `places`)
- **Modèle** : nom, lat/lng, adresse, catégorie (11 types), `day` (1-based, `null` = non planifié), heure de début, durée, coût estimé, `order`, notes.
- **Routes** :
  - CRUD, liste filtrable par jour, catégorie et nom.
  - `PUT /places/reorder` : réordonne les lieux d'un jour, utilisé par le glisser-déposer.
  - `GET /geocode?q=` : proxy vers Nominatim avec cache mémoire.
  - `GET /route?day=N` : appelle OSRM.
- **Calcul d'itinéraire** ([route.service.ts](trip-planner-api/src/modules/places/route.service.ts)) :
  - OSRM donne la distance, la durée en voiture et la géométrie de la route.
  - Si OSRM est injoignable, on bascule sur une **estimation** : distance à vol d'oiseau (Haversine) ×1,3, à 40 km/h en voiture et 4,5 km/h à pied.
  - Résultat mis en cache 6 h.
- **Front** :
  - La page [itinerary](trip-planner-web/src/app/trips/[id]/itinerary/page.tsx) affiche la carte et la liste par jour, avec glisser-déposer, filtre par jour et temps de trajet entre étapes.
  - [TripMap.tsx](trip-planner-web/src/components/map/TripMap.tsx) affiche des marqueurs numérotés avec une couleur par jour et des polylignes de route.
  - Hors ligne, les trajets sont recalculés localement en estimation.
- **Fonctionnalité avancée :** carte interactive avec trajet quotidien.

### Module 4 : Dépenses (`modules/expenses/`, collection `expenses`)
- **Modèle** : le montant est stocké en **devise d'origine et en devise de base du voyage** (`amountInBase`, `rateUsed`). Il contient aussi le payeur, la liste des personnes qui se partagent la dépense, et un reçu optionnel.
- **Taux de change** ([rates.service.ts](trip-planner-api/src/modules/expenses/rates.service.ts)) :
  - Appel de `open.er-api.com` au plus une fois par jour par devise.
  - En cas d'échec, une table de repli de 34 devises est utilisée et le service réessaie après 1 h.
- **Résumé budget** (`GET /expenses/summary`) :
  - Totaux, répartition par catégorie et par jour.
  - **Alerte à 80 %** du budget.
  - Soldes par personne.
  - Règlements « qui doit à qui » par algorithme glouton : le plus gros débiteur paie le plus gros créancier.
- **Front** ([expenses/page.tsx](trip-planner-web/src/app/trips/[id]/expenses/page.tsx)) :
  - Le même calcul est refait **côté client** (`summarize`) pour fonctionner hors ligne.
  - Hors ligne, la conversion est une estimation avec les derniers taux en cache (`estimateInBase`, drapeau `pendingConversion`).
  - Les graphiques camembert et barres sont dans [ExpenseCharts.tsx](trip-planner-web/src/components/trips/ExpenseCharts.tsx).
- **Fonctionnalité avancée :** conversion multi-devises et graphiques de budget.

### Module 5 : Checklist (`modules/checklist/`, collections `checklist_items` et `checklist_templates`)
C'est le module le plus original côté logique.
- **Moteur de règles piloté par les données** ([generator.ts](trip-planner-api/src/modules/checklist/generator.ts)) :
  - Les règles sont stockées en base sous forme de JSON : `{always}`, `{field, op, value}`, `{any:[...]}`, `{all:[...]}`.
  - Opérateurs : `eq`, `neq`, `in`, `includes`, `gt`, `gte`, `lt`.
  - Les 18 modèles sont dans [seed/templates.ts](trip-planner-api/src/seed/templates.ts) : toujours, plage, montagne/randonnée, camping, plongée, photo, avion, voiture, bébé, hiver, été, à l'étranger, tenue de soirée, conduite à l'étranger, tenue modeste, business, ski, natation.
- **Contexte** : les préférences du voyage, plus des valeurs **dérivées** :
  - la saison, avec inversion dans l'hémisphère sud ([lib/countries.ts](trip-planner-api/src/lib/countries.ts)) ;
  - la durée ;
  - un drapeau « à l'étranger », calculé en comparant le pays de destination au pays d'origine du propriétaire.
- **Quantités** : pour les articles « comptables » (sous-vêtements, chaussettes), `min(durée+1, 10) × adultes`.
- **Resynchronisation intelligente** (`syncChecklist`) :
  - Elle ajoute les articles manquants.
  - Elle met à jour la quantité ou la catégorie des articles générés non touchés.
  - Elle supprime les articles générés devenus inutiles.
  - Elle **ne touche jamais** à un article édité (`isEdited`) ou déjà coché.
  - Elle est déclenchée à la création du voyage et à chaque changement de préférences, de dates ou de pays.
- **Fonctionnalité avancée :** checklist générée depuis les préférences.

### Module 6 : Journal (`modules/journal/`, collection `journal_entries`)
- **Contenu** : titre, texte jusqu'à 10 000 caractères, jusqu'à 12 photos, date, humeur (5 valeurs), lieu lié (vérifié comme appartenant au voyage) et coordonnées GPS.
- **Droits** : seul l'auteur modifie ou supprime son entrée.
- **Front** : bouton « me localiser » via `navigator.geolocation`, upload de photos via `/uploads`, fonctionne hors ligne.
- **Fonctionnalité avancée annoncée : « AI itinerary generator (to do) »**. Elle n'est **pas implémentée**, le README le dit lui-même.

### Module 7 : Forum (`modules/forum/`, collections `forum_posts` et `forum_replies`)
Le plus riche en règles métier ([forum.routes.ts](trip-planner-api/src/modules/forum/forum.routes.ts)).
- **Lecture publique** (`optionalAuth`) :
  - Recherche **plein texte** via un index texte MongoDB, titre pondéré ×3 par rapport au corps.
  - Filtres par catégorie (8) et par tag de destination, tri par pertinence, récent, top ou actif.
  - Nuage de tags populaires.
- **Écriture** (en ligne uniquement, volontairement) :
  - Un post demande un titre de 10 à 120 caractères, un corps de 20 à 5000 et de 1 à 5 tags.
  - Les réponses ont une **limite d'une par minute**, et les commentaires de réponse sont limités à **un seul niveau** et 500 caractères.
  - Un vote par personne et par élément, réversible (opérations atomiques `$addToSet` / `$pull`).
  - Un marqueur « édité » apparaît après 30 min.
- **Suivi et push** :
  - L'auteur suit son post automatiquement, et toute personne qui répond suit aussi le fil.
  - Les followers reçoivent une notification Web Push, sauf s'ils ont désactivé le fil ou la préférence globale.
  - Les abonnements push expirés (404/410) sont supprimés automatiquement ([lib/push.ts](trip-planner-api/src/lib/push.ts)).
- **Modération** : signalement (un seul par personne et par contenu), file de modération admin avec les actions hide, unhide, lock, unlock, delete et dismiss. Un compte supprimé laisse son contenu anonymisé (« Deleted user »).
- **Fonctionnalité avancée :** recherche plein texte et notifications push.

### Module transversal : Uploads (`modules/uploads/`)
`POST /uploads?folder=receipts|journal|misc` accepte jusqu'à 6 images. Elles partent sur Cloudinary (converties en WebP) si les clés sont configurées. Sinon, elles sont écrites dans `./uploads` et servies en statique avec un cache de 30 jours.

## 7. Le front PWA, la partie « offline-first »

C'est le cœur du projet. Trois couches coopèrent.

### a) IndexedDB avec Dexie ([lib/db.ts](trip-planner-web/src/lib/db.ts))
- Base `trip-planner` avec les tables `trips`, `places`, `expenses`, `checklist`, `journal`, `outbox` et `meta`.
- Les pages lisent **toujours la copie locale** via `useLiveQuery` ([lib/hooks.ts](trip-planner-web/src/lib/hooks.ts)). Elles fonctionnent donc sans réseau.
- `pullTrip` télécharge le voyage complet (`/full`) quand le réseau est là, sans écraser les documents qui ont des modifications en attente.

### b) Moteur de synchronisation ([lib/sync.ts](trip-planner-web/src/lib/sync.ts))
- Chaque écriture est **appliquée localement d'abord**, puis mise dans la file `outbox`. Les `_id` sont générés côté client ([lib/objectId.ts](trip-planner-web/src/lib/objectId.ts), un faux ObjectId MongoDB), ce qui rend les créations rejouables sans doublon.
- Le rejeu se fait dans l'ordre :
  - Il s'arrête au premier échec réseau.
  - En cas de 409, la version serveur est conservée et l'utilisateur est prévenu.
  - Une erreur 4xx fait abandonner l'opération.
  - Les erreurs 5xx ou 429 sont réessayées plus tard.
- Il est déclenché par l'événement `online`, par un test de connectivité toutes les 15 s, au retour de visibilité de l'onglet, ou par le bouton de [SyncIndicator](trip-planner-web/src/components/SyncIndicator.tsx).
- Un verrou `navigator.locks` évite que deux onglets rejouent en même temps.

### c) Service Worker ([public/sw.js](trip-planner-web/public/sw.js))
- **Précache** de l'« app shell » (`/`, `/offline`, `/trips`, `/forum`, `/login`).
- **Stratégies de cache :**
  - pages : réseau d'abord, avec repli sur le cache ;
  - `/_next/static` et icônes : cache d'abord ;
  - tuiles OpenStreetMap : cache d'abord (400 max) ;
  - lectures API d'affichage (taux, résumé budget, route, templates, partage) : stale-while-revalidate ;
  - les 50 derniers posts de forum ouverts : réseau d'abord, repli cache.
- **Données de voyage** : jamais mises en cache par le SW, puisque IndexedDB s'en charge.
- **Web Push** : affichage de la notification et ouverture de la bonne URL au clic.
- **Background Sync** : rejoue l'`outbox` même quand l'app est fermée (Chromium). Il ouvre directement IndexedDB et réimplémente la même logique que `sync.ts`.
- **Version de cache** `v2` : les anciens caches sont purgés à l'activation.

### d) Autres éléments PWA
- **Manifest** ([manifest.ts](trip-planner-web/src/app/manifest.ts)) : mode `standalone`, couleur `#0f766e`, icônes normales et maskable, raccourcis « My trips » et « Forum ».
- **[InstallPrompt](trip-planner-web/src/components/InstallPrompt.tsx)** : bouton d'installation via `beforeinstallprompt` sur Chrome, Edge et Android. Sur iOS, un guide « Ajouter à l'écran d'accueil » s'affiche.
- **[ServiceWorker.tsx](trip-planner-web/src/components/ServiceWorker.tsx)** : enregistre le SW en production seulement, sauf si `NEXT_PUBLIC_ENABLE_SW=true`. Il demande aussi au SW de mettre en cache chaque page visitée.
- **Session hors ligne** ([lib/auth.tsx](trip-planner-web/src/lib/auth.tsx)) : si l'API est injoignable, l'utilisateur mis en cache dans `localStorage` est réutilisé. À la déconnexion ou au changement de compte, les données locales et les caches API sont effacés.
- **Client API** ([lib/api.ts](trip-planner-web/src/lib/api.ts)) :
  - Le token d'accès est gardé en mémoire.
  - En cas de 401, un refresh est tenté une seule fois, avec un « single-flight » : les appels simultanés partagent la même requête de refresh.
  - `NetworkError` et `ApiError` sont distingués.
- **Permission de notification** : demandée uniquement après une action de l'utilisateur (poster, suivre, profil), jamais au chargement.

## 9. Sécurité (résumé)
- **Authentification** : access token JWT court en mémoire, refresh en cookie httpOnly avec rotation et détection de réutilisation.
- **Mots de passe** : bcrypt avec coût 12.
- **Entrées** : zod valide chaque entrée. Les regex de recherche sont échappées (`escapeRegex`) et les champs de tri sont limités à une liste blanche.
- **Contrôle d'accès** : par appartenance au voyage, avec un statut `owner` ou `editor` pour les actions sensibles.
- **Protection générale** : helmet, CORS restreint à `CLIENT_ORIGIN`, rate limiting, en-têtes de sécurité côté Next.js.
- **Compte** : l'utilisateur doit retaper son mot de passe pour supprimer son compte.

## 10. Points d'attention

1. **Fonctions non faites** (README de l'API) : générateur d'itinéraire par IA, règles météo, CI et **tests automatisés (aucun)**.
2. **Cohérence du README** : la table des modules liste « AI itinerary generator (to do) » comme fonction avancée du Journal, alors qu'elle n'existe pas dans le code.
3. **Caches en mémoire** (géocodage, itinéraires, taux) : sans limite de taille pour `geoCache`, et perdus à chaque redémarrage. Ça passe pour un projet de cours, moins pour de la production.
4. **Fichiers locaux** : sans Cloudinary, `./uploads` est un disque local, qui disparaît sur un hébergeur éphémère. De plus, `/uploads` est servi sans authentification, mais les noms sont aléatoires (12 octets).
5. **Conflits « last-write-wins »** : une modification offline peut être écrasée par une version serveur plus récente, avec seulement une notification.
6. **iOS** : pas de Background Sync, et le push demande iOS 16.4+ avec l'app installée.

# Rôles et cas d'usage de Trip Planner

Il y a deux niveaux de rôles dans l'application : les **rôles globaux** (compte) et les **rôles dans un voyage**. S'y ajoutent deux statuts liés au contenu, l'auteur et le lecteur d'un lien de partage.

## 1. Les rôles

### Rôles globaux (champ `role` du compte)
| Rôle | Qui | Ce qu'il peut faire |
|---|---|---|
| **Visiteur** (non connecté) | Toute personne sans session | Voir la landing page, lire le forum (posts publiés, tags, catégories), ouvrir un lien de partage `/share/<token>`, consulter les taux de change, s'inscrire ou se connecter |
| **Membre** (`member`) | Tout compte créé | Tout ce qui concerne ses voyages, plus écrire dans le forum et gérer son profil |
| **Administrateur** (`admin`) | Compte promu par un autre admin, ou compte du seed | Page `/admin` : statistiques, file de modération, gestion des utilisateurs. Peut aussi supprimer n'importe quel post ou réponse |

L'admin n'a **pas** accès automatiquement aux voyages des autres : l'accès à un voyage dépend uniquement de l'appartenance à sa liste de participants.

### Rôles dans un voyage (champ `members[].role`)
| Rôle | Droits |
|---|---|
| **Owner** (propriétaire, le créateur) | Tout ce que fait un editor, plus : **supprimer le voyage**, **inviter** des participants, **retirer** n'importe quel participant, **créer et révoquer le lien public** |
| **Editor** (participant invité) | Voir et modifier le voyage (détails, préférences), ajouter ou modifier lieux, dépenses et checklist, écrire dans le journal, changer la couverture, exporter le PDF, **quitter** le voyage |

### Statuts liés au contenu
- **Auteur d'une entrée de journal :** seul lui peut la modifier ou la supprimer. Les autres participants la lisent.
- **Auteur d'un post ou d'une réponse de forum :** seul lui peut l'éditer. Il peut la supprimer, comme un admin.
- **Lecteur d'un lien de partage :** accès en lecture seule à l'itinéraire (lieux et jours). Il ne voit ni budget, ni journal, ni checklist.

## 2. Matrice de permissions

| Action | Visiteur | Membre | Editor du voyage | Owner du voyage | Admin |
|---|:-:|:-:|:-:|:-:|:-:|
| Lire le forum | ✅ | ✅ | ✅ | ✅ | ✅ |
| Poster, répondre, voter, signaler | ❌ | ✅ | ✅ | ✅ | ✅ |
| Créer un voyage | ❌ | ✅ | ✅ | ✅ | ✅ |
| Modifier lieux, dépenses, checklist | ❌ | ❌ (pas membre du voyage) | ✅ | ✅ | ❌ (sauf s'il est participant) |
| Inviter ou retirer quelqu'un | ❌ | ❌ | ❌ (il peut seulement se retirer lui-même) | ✅ | ❌ |
| Créer ou révoquer le lien public | ❌ | ❌ | ❌ | ✅ | ❌ |
| Supprimer le voyage | ❌ | ❌ | ❌ | ✅ | ❌ |
| Modérer le forum | ❌ | ❌ | ❌ | ❌ | ✅ |
| Désactiver un compte, changer un rôle | ❌ | ❌ | ❌ | ❌ | ✅ (pas sur son propre compte) |

# Le processus d'invitation, étape par étape

Ce qui suit vient du code ([InviteForm.tsx](trip-planner-web/src/components/trips/InviteForm.tsx) et la route `POST /trips/:tripId/members` dans [trip.routes.ts](trip-planner-api/src/modules/trips/trip.routes.ts)). Je n'ai pas testé le flux dans le navigateur.

**L'invitation est immédiate et sans acceptation.** Si l'email correspond à un compte existant, la personne est ajoutée directement au voyage, sans email, sans notification et sans étape de confirmation de sa part.

## 1. Côté interface
1. L'**owner** clique sur « Invite people → » (Overview) ou utilise la section Participants des réglages. Un participant simple voit un message à la place du formulaire.
2. Il saisit un email. Le bouton **Invite** reste désactivé tant que le champ est vide ou que l'application est **hors ligne** : l'invitation est une action « en ligne uniquement » et ne passe pas par la file de synchronisation.
3. À l'envoi, l'application appelle `POST /api/v1/trips/<id>/members` avec `{ "email": "..." }`.

## 2. Côté API : les contrôles, dans l'ordre
| # | Contrôle | Échec |
|---|---|---|
| 1 | Token d'accès valide et compte actif | 401 |
| 2 | Le voyage existe | 404 « Trip not found » |
| 3 | L'appelant est participant du voyage | 403 « You are not a member of this trip » |
| 4 | L'appelant est **owner** | 403 « Only the trip owner can do this » |
| 5 | L'email est valide (mis en minuscules) | 400 avec l'erreur sur le champ `email` |
| 6 | Un compte **actif** existe avec cet email | 404 « No member account uses this email - ask them to register first » |
| 7 | La personne n'est pas déjà participante | 409 « This person is already a participant » |

Si tout passe, l'API ajoute `{ user, role: 'editor', joinedAt: maintenant }` à la liste des participants, sauvegarde, et renvoie le voyage mis à jour avec les noms, emails et avatars des participants.

Le rôle est **toujours `editor`**. On ne peut pas choisir un autre rôle à l'invitation. Inviter sa propre adresse donne l'erreur 409 de l'étape 7.

## 3. Retour dans l'interface
- **Succès :** le voyage mis à jour est enregistré dans IndexedDB. La liste des participants se rafraîchit toute seule (lecture « live »), le message « Participant added » s'affiche et, depuis l'Overview, la fenêtre se ferme.
- **Échec :** le message d'erreur de l'API s'affiche sous le champ email, par exemple celui de l'étape 6. Si le réseau est coupé, le message est « You appear to be offline ».

## 4. Ce que vit la personne invitée
- Elle ne reçoit **aucune notification** (ni email, ni push).
- Le voyage apparaît dans **sa liste « My trips »** la prochaine fois que son application recharge cette liste, c'est-à-dire à l'ouverture de la page `/trips`. Il n'y a pas de rafraîchissement automatique en arrière-plan pour ça.
- Elle devient **editor** : elle peut modifier le voyage, ajouter des lieux, des dépenses, des éléments de checklist, écrire dans le journal, exporter le PDF, et **quitter** le voyage.
- Elle ne peut **pas** inviter, retirer d'autres personnes, créer ou révoquer le lien public, ni supprimer le voyage.

## 5. Effets sur le reste du voyage
- **Dépenses :** la nouvelle personne est incluse dans le partage des dépenses **créées après son arrivée** (par défaut, un nouveau coût se répartit entre tous les participants du moment). Les dépenses déjà saisies gardent leur liste d'origine : elle n'y est pas ajoutée.
- **Checklist :** inchangée. Elle dépend des préférences du voyage et du pays d'origine du **propriétaire**, pas du nombre de participants.
- **Lien public :** inchangé. Le prénom de la personne apparaît ensuite dans la liste des participants de la page publique.
- **Retrait :** l'owner peut retirer la personne à tout moment. Ses anciennes dépenses restent, avec le nom « Former participant » dans le résumé du budget.

## 6. Limites actuelles
1. **Pas de consentement :** n'importe quel propriétaire peut ajouter une personne à un voyage, qui ne peut que le quitter après coup.
2. **Pas d'invitation en attente :** si la personne n'a pas de compte, l'invitation est refusée au lieu d'être mise en attente. Il n'y a ni lien d'invitation ni email envoyé.
3. **Divulgation d'existence de compte :** les erreurs de l'étape 6 permettent de savoir si une adresse email a un compte. Le « mot de passe oublié » fait l'inverse volontairement, avec une réponse identique dans les deux cas. Les invitations sont limitées par le même plafond général de 300 requêtes par minute.
4. **Rôle unique** (`editor`) et pas de transfert de propriété.
5. **Pas de notification** à la personne ajoutée, ni de journal « qui a invité qui ».

Ces points correspondent à la proposition B de mon analyse précédente : invitations par lien à durée limitée, email envoyé avec `sendMail` (déjà dans l'API), rôle lecteur, acceptation par l'invité. Je peux l'implémenter si vous voulez en faire votre fonctionnalité avancée.

Il y a trois façons de procéder. Elles ne se valent pas : pour un projet comme le vôtre, évitez de monter votre propre serveur mail.

## Option 1 : un fournisseur SMTP (recommandé pour envoyer de vrais emails)

|---|---|---|

Techniquement possible, mais je le déconseille ici. Ce qui rend cela difficile n'est pas l'installation, c'est que les emails **arrivent en spam ou sont refusés** sans :
- un **nom de domaine** à vous ;
- des enregistrements DNS **SPF, DKIM et DMARC** ;
- une **IP fixe avec DNS inverse** et une bonne réputation ;
- un **port 25 sortant ouvert** : la plupart des box et hébergeurs le bloquent.

Sans cela, Gmail et Outlook rejettent ou classent le message en indésirable.

Si vous avez un domaine et que vous voulez des emails fiables, le bon chemin est l'option 1 avec ce domaine. Le fournisseur vous donne les enregistrements DNS à ajouter.

## Option 3 : un serveur mail local pour développer (Mailpit dans Docker)
Vous avez déjà Docker, et c'est le cas où « configurer un serveur mail » a vraiment du sens. Mailpit est un **faux serveur SMTP local** : il reçoit les emails de l'API et les affiche dans une boîte de réception web, sur http://localhost:8025. Rien n'est envoyé sur Internet.

Il suffit d'ajouter ce service à `docker-compose.yml` :

```yaml

    image: axllent/mailpit
    ports:
      - "1025:1025"   # SMTP
      - "8025:8025"   # interface web
```

Puis dans `.env` : `SMTP_HOST=localhost`, `SMTP_PORT=1025`, et laissez l'utilisateur et le mot de passe vides. Le mailer de l'API gère déjà ce cas (pas d'authentification si `SMTP_USER` est vide).
